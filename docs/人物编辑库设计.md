# 人物编辑库（作品级人物唯一性）设计 · 已实现

> **状态：已实现（2026-10-29，v3 人物库）。** 实现记录见 `docs/开发进度.md` 同日条目。
> 本文保留原设计全文作为设计依据；与实现不一致处，以本文「实现差异」小节为准。

## 0. 实现差异（与原设计的偏差，均经用户豁免授权）

原设计的迁移向导（§5）与五步合并向导（§8）按用户豁免大幅简化——**无需考虑迁移兼容，无法兼容的旧人物数据可直接删除**：

- **一次性提取（替代 §5 全部迁移向导/别名表/冲突报告）**：persist v3 起人物库存放在 `SimState.characters`；旧档（v2.31 带 states 的节点 / 更早的平铺字段）载入时按「画布键序 × 节点序」扫描，以**旧 node.id 作为 characterId** 建库（图片 key `charimg:<nodeId>:…` 天然继续有效，C10）。同 ID 镜像首见保留，分叉副本静默丢弃；已是放置形态（`data.characterId` 存在）的节点跳过不重复建库；幂等。无向导、无别名表、无冲突报告。
- **简单手动合并（替代 §8 五步向导）**：人物库面板对同名重复项提供「合并」入口，`CharacterMergeDialog` 选主人物 → 预览（状态追加、标签冲突加「（N）」、受影响放置/章节计数）→ `window.confirm` 确认 → `mergeCharacters(primaryId, otherIds)` 一次完成（状态追加去重、放置与快照引用改写、他板重复放置去重、图片 GC）。
- **存档版本**：`ARCHIVE_VERSION` 3→4（`graph.characters` 必填）；v3 旧档导入时执行同一一次性提取并提示「N 人已迁入人物库」。
- **持久化版本**：persist `version: 3` + `migrate: (s) => s` 直通（升版本无 migrate 会在 merge 前丢数据=用户丢档）；merge 内做提取与画布清洗。
- **决策采用（§14）**：C1 当前状态按放置独立（`activeStateId` 在放置上）；C4 一人一画布一个放置（sanitize 重复保留首个）；C5 画布删节点=仅移除放置，全局删除只在人物库 UI；C6 复制为新保留（新库记录+图片 key 重写+imageTasks 异步复制字节）；C7 允许未放置人物；C9 顶栏「人物库」入口与「查人」并列（带人数徽标）；C10 旧图片 key 不改名。
- **旧平铺人物提取的额外决策**：提取门槛只看「是否已是放置形态」（`data.characterId` 非空），不看 `states` 是否为数组——保证 v2.31 之前的纯平铺人物节点（无 states 字段）也进库（设计文档原测试矩阵第 323 行要求）。

## 1. 需求

一个作品内，人物应当是唯一的：

- 第一卷的张三和第二卷的张三，是**同一个人物的两次放置**；
- 不同章、卷的画布节点只决定这个人物**出现在哪里、当前用哪个状态**；
- 人物的姓名、性别、状态（年龄/基础信息/身份信息/关系/形象大图/头像）只存一份，任何一处编辑，所有卷/章立即读到同一份数据；
- 章节快照、正文/大纲生成、跨卷查人、人物时间轴、编辑 Agent 都按同一个 `characterId` 解析人物；
- 允许同名但确实是两个不同角色（同名不同人），但绝不自动合并，合并必须由用户明确确认。

**当前不做的范围**：跨设备/跨浏览器图片同步、状态属性的历史版本、按名字或相似度自动合并、多个作品共享同一人物库、章节画布的时间旅行。

## 2. 现状：为什么现在没有关联

当前系统里没有“人物”实体，人物就是某张画布上的一个节点：

| 事实 | 位置 |
|---|---|
| `CharacterData` 直接放在 `SimNodeType.data` 中，包含 `name/gender/states/activeStateId` | `src/types/sim.ts:106-128` |
| `boards` 是节点唯一权威数据源，卷画布 1:1 | `src/types/sim.ts:245-254` |
| 镜像复制是**深拷贝节点数据**并保留 node.id；复制为新则换新 ID | `src/stores/boardCopy.ts:130-165`、`210-243` |
| 所有人物编辑动作都带 `boardId`，只改当前画布节点 | `src/stores/studioStore.ts:1354-1549` |
| 节点 ID 只在单张画布内唯一；镜像跨画布共享同一 ID | `src/stores/studioStore.ts:304-315` |
| 章节快照的 `characterId` 实际就是节点 ID，解析需结合 `boardId` | `src/types/sim.ts:172-195`、`src/stores/snapshotRefs.ts:58-90` |
| 人物形象 key 以 nodeId 为前缀 | `src/stores/characterStates.ts:38-45` |
| 查人遇到同名会标歧义，绝不合并 | `src/stores/characterSearch.ts:41-95` |
| 未保存脏检查只比较 `boards` 与章节；人物数据一旦移出 `boards`，必须同步纳入 | `src/stores/studioStore.ts:725-753` |
| 删除卷直接删板，不释放人物图片 key（现有悬空图片问题） | `src/stores/studioStore.ts:863-879` |
| 章节场景自动同步只订阅 `boards` | `src/stores/chapterSceneSync.ts:60-90` |

另：设计文档 D8 当时明确选择了“跨卷复制后独立演化、不做实时联动”（见
`docs/章节画布与人物状态设计.md` §12 D8、§5.5），所以当前表现是既有产品决定，不是缺陷。

**结论**：要实现人物唯一性，必须把“人物属性”从画布节点中拆出来，变成一个作品级的独立集合；画布节点退化为“放置 + 当前状态”。

## 3. 目标数据模型

### 3.1 人物库（作品级，唯一数据源）

```ts
/** 作品级人物：身份与全部状态定义只存这一份 */
export interface WorkCharacter {
  id: string;                 // 人物库 ID，作品内唯一；旧数据迁移时沿用原 node.id
  name: string;
  gender: CharacterGender;
  /** 至少一项；首项=默认状态。状态属于人物，不属于某张画布 */
  states: CharacterState[];
}

/** 放在 SimState 顶层，随作品状态/存档一起保存 */
characters: Record<string, WorkCharacter>;
```

说明：

- `CharacterState` 保持现有结构（含 `age/basicInfo/identityInfo/relations/image`），不做改动。
- `WorkCharacter` **不含 `activeStateId`**：当前状态是场景信息，不属于人物身份。

### 3.2 画布节点（放置信息）

```ts
/** 人物节点：只保存“谁放在这里、当前显示哪个状态、放在哪” */
export interface CharacterPlacementData extends Record<string, unknown> {
  kind: 'character';
  characterId: string;        // 指向 characters
  activeStateId: string;      // 本画布当前使用的状态；按画布独立
}

// 位置、父子、尺寸、zIndex、edges 仍属于 SimBoard.nodes / React Flow，不变
```

约束：

- 同一张画布内，一个 `characterId` 最多一个放置节点（一人一卷一次）；跨画布可重复放置。
- 放置节点的 `node.id` 只是画布内部 ID，可以继续沿用旧 node.id；**人物身份一律以 `characterId` 为准**。
- 建议 `characterId` 与放置节点 ID 解耦：以后链接/合并/重新放置都不需要改画布节点 ID，也不会影响快照里的定位。

### 3.3 章节快照

`ChapterSnapshotEntry` 改为：

- `characterId`：改为人物库 ID（不再等于画布节点 ID）；
- `stateId`：人物库内状态 ID；
- `boardId`（快照级）继续保留：表示该章场景发生在哪张画布，用于切章回放；
- 场景回放时：先在 `snapshot.boardId` 画布上按 `characterId` 找放置节点，再恢复位置/父环境/当前状态。

不再需要“跨卷同 ID 唯一回退/同名歧义”的逻辑：人物库全局唯一，解析结果只可能是“人物存在/缺失、状态存在/缺失”。

## 4. 关键业务规则

1. **属性编辑全局生效**：姓名、性别、状态内容、形象、头像的修改，写入 `characters`；所有卷/章的放置节点立即读到新值。
2. **当前状态按放置独立**：第一卷可显示“常态”，第二卷可显示“黑化后”；切换状态只改放置节点的 `activeStateId`，不写人物库。
3. **新增/重命名/删除状态属于人物库**：删除状态前需检查所有放置节点的 `activeStateId` 与所有章节快照引用；删除后相关放置回落到首项状态并提示。
4. **同人物多卷不复制属性**：镜像放置只引用 `characterId`，不复制状态/图片。
5. **同名不同人不自动合并**：允许存在两个 `name` 相同但 `characterId` 不同的角色；管理器可给出“疑似重复”提示，合并必须由用户确认。
6. **两种删除语义必须分开**：
   - “从本画布移除”：只删除放置节点，人物仍在库中；
   - “删除人物”：从人物库删除，移除所有放置节点，并列出将受影响的章节快照；需二次确认。
7. **“复制为新”保留**：有意创建独立角色时，复制人物库记录（新 `id`）+ 新放置节点；图片按新 key 复制字节，语义与现在一致。
8. **人物可只存在于库中**：允许尚未放到任何画布的人物（用于提前建人设）；管理器需要展示“未放置”。
9. **章节生成**：人物属性从人物库解析，位置/父环境/当前状态从该章快照或放置节点解析；名单锁规则不变。

## 5. 迁移（最高风险项）

### 5.1 基本映射

1. 扫描全部 `boards[].nodes` 中 `kind === 'character'` 的节点。
2. 以旧 `node.id` 建立人物库：`characterId = node.id`（这样历史快照的 `characterId` 继续有效）。
3. 节点数据改为 `{ kind:'character', characterId, activeStateId }`；位置/父环境/尺寸保留。
4. 旧 `states` 迁入对应 `WorkCharacter.states`；`activeStateId` 留在放置节点。
5. 图片 key **不强制改名**：旧 `charimg:<nodeId>:...` 字符串继续有效；新写入的 key 改用 `charimg:<characterId>:...`。GC 改为扫描人物库。

### 5.2 镜像副本（跨画布共享 node.id）的合并

- 若各卷的镜像副本内容（去掉 `activeStateId` 后）**完全一致**：直接合并为一个人物，自动完成。
- 若内容已分叉：**不能静默选一份**。迁移时需要冲突报告，让用户选择：
  - 以某一卷为准（其它卷的差异丢失前明确提示）；
  - 把差异状态保留为额外状态（推荐，如“第一卷版本”“第二卷版本”）；
  - 暂不合并，拆成两个人物并改写受影响的快照引用（需要别名机制）。
- 迁移结束后提供一份“合并/拆分/冲突”清单，可回看。

### 5.3 同名不同 ID

- 默认**不合并**，迁移后是两个人物。
- 管理器标记“疑似同一人”（规范化姓名相同）并允许手动合并；合并时处理状态 ID 冲突、图片归属与快照引用。

### 5.4 快照兼容与别名

- 迁移后旧快照 `characterId` = 旧 node.id，仍能命中人物库。
- 如果某次合并/拆分改写了人物 ID，需要保存别名表 `characterAliases: Record<旧ID, 新ID>`，解析快照时跟随别名；时间轴与查人同样跟随。别名表随作品存档。

### 5.5 存档与持久化

- persist：继续在 `merge` 中做结构迁移（当前 `nc2-sim-v1` version 2 没有 `migrate`，升版本会丢档，见 `src/stores/studioStore.ts:1708-1749`）。
- 命名存档：`ARCHIVE_VERSION` 从 3 升到 4；`normalizeArchive` 增加 v3→v4 迁移；导出输出 v4；导入继续接受 v3。
- `replaceState` / 载入存档 / 新建作品必须整体替换 `characters`，否则切换作品会串人物库。
- **脏检查必须包含人物库**：`sameStudioContent`（`src/stores/studioStore.ts:725-753`）现在只比较 `boards`/章节；人物属性移出 `boards` 后，只改人物库不会触发“未保存”提示，必须把 `characters` 纳入比较，并确认 `manualPersistStorage` 的 payload 包含它。
- 人物库“作品级”边界：一个作品 = 当前 `useStudioStore` 状态（及对应命名存档）；不需要额外的 `workId` 才能成立。若以后要严格隔离图片，可把 `workId` 加进图片 key。

## 6. 人物形象与图片

- 人物形象/头像属于**状态**，状态属于人物库；同一人物在多个卷共享同一张图。
- 旧 key 继续保留；新 key 使用 `charId`：`charimg:<characterId>:<stateId>:<nonce>`、`charhead:...`。
- `collectReferencedImageKeys` 从“扫描所有画布状态”改为“扫描人物库”；删除放置节点不再触发图片 GC，只有删除状态/人物才触发。
- “复制为新人物”与现在“复制为新”一致：生成新人物 ID、新图片 key，并异步复制 IndexedDB 字节。
- 导出仍只含元数据，不含图片字节；跨浏览器导入后按现有规则提示缺失、回退性别剪影。

## 7. Store / 动作边界

### 7.1 新增人物库动作

```ts
createCharacter(character, opts?: { placeOnBoardId?: string; pos?: XYPosition }): string
updateCharacterIdentity(characterId, { name?, gender? })
addCharacterState(characterId, opts?)
updateCharacterState(characterId, stateId, patch)
renameCharacterState(characterId, stateId, label)
deleteCharacterState(characterId, stateId)
linkPlacement(boardId, characterId, pos, parentId?)
unlinkPlacement(boardId, nodeId)           // 从画布移除，不删人物
deleteCharacter(characterId)               // 全局删除，带引用报告
mergeCharacters(primaryId, otherIds, opts) // 管理器合并
```

### 7.2 放置动作

- 复用现有 `addNode` / `deleteNode` / `reparentNode` / 拖动坐标逻辑，但人物节点只写 `{ characterId, activeStateId }`。
- `switchCharacterStateOnBoard` 保留，只改放置节点 `activeStateId`。
- 旧的 `updateCharacterOnBoard` / `*CharacterStateOnBoard` 建议删除或改为兼容层：先定位放置节点，再改写人物库（避免两套写入口）。

### 7.3 创建与落地

- 画布手动新建人物：先建人物库记录，再建放置节点。
- 编辑室【人物设定】落地：先按人物 ID / 名字查库；命中则更新，未命中则新建人物库记录并放置到目标卷。
- 跨卷写入：人物身份修改不再需要“卷”消歧；“卷”只决定放置位置与当前状态。
- 删除卷：只删该卷画布与放置节点，人物库保留；同时补上现有“删卷不释放图片 key”的漏洞（改为按人物库引用统一 GC）；提供“清理从未放置的人物”入口（可选）。
- 章节场景同步：`chapterSceneSync` 目前只订阅 `boards` 变化。状态属性（basicInfo/relations/image 等）迁入人物库后，属性修改不会再触发场景快照指纹刷新；需要同时订阅 `characters`，或明确只在切章/生成前重算指纹。

## 8. 管理器 UI（人物编辑库）

入口建议：顶栏“人物库”（可与现有“查人”合并）/ 属性面板人物节点上的“打开人物库”。

列表：

- 全部人物：姓名、性别、状态数、是否已放置、出现卷/章数量、疑似同名标记；
- 搜索：复用 `normalizeCharacterName`；
- 筛选：已放置 / 未放置 / 疑似重复。

详情：

- 编辑姓名、性别、全部状态（与当前属性面板的人物编辑区一致）；
- 形象大图上传/AI 生成/裁切头像（复用现有 `CharacterImageSection` 与裁切弹窗）；
- 使用位置：在哪些卷画布放置、被哪些章快照引用（可跳转/定位）；
- 操作：在当前画布放置、链接已有节点、新建人物、删除人物、合并人物。

合并向导：

1. 选择主人物与待合并人物；
2. 展示姓名/状态差异；
3. 状态按 `state0`、其余状态按标签/内容对齐，冲突逐项选择保留；
4. 预览受影响的画布放置与章节快照；
5. 确认后改写放置 `characterId`、快照引用（或写别名表），必要时删除同板重复放置。

移动端：列表单列，详情全屏，合并向导分步，避免横向溢出。

## 9. 编辑 Agent 协议调整

- 人物身份是作品级的：修改姓名/状态/属性会影响所有卷；系统提示必须明确这一点。
- “卷：”字段语义从“人物身份消歧”变为“放置目标/当前画布”；未写卷时默认当前画布，用于放置与切状态。
- 人物库检索：跨全作品检索，返回人物 ID、姓名、已放置卷与当前各卷状态；同名不同人继续标记歧义。
- 【人物设定】更新时按 `characterId` 精确匹配；同名多人物必须让用户选择或带 ID，不能静默挑选。
- 【人物状态】新建/修改/切换/重命名/删除：前三者中“修改”写人物库，“切换”写当前放置；删除状态前列出受影响的卷与章节。
- Agent 不得在未提示的情况下创建与已有同名的新人物；应提示“链接已有/新建独立角色”。
- 章节上下文：快照 `characterId` 直接解析人物库；缺少放置时仍可读出属性，但回放位置时标记“本画布未放置”。

## 12. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 镜像副本已分叉 | 自动合并会丢设定 | 迁移冲突报告 + 用户选择；差异可保留为额外状态 |
| 同名不同人被误合并 | 两个角色被揉成一个 | 绝不按名字自动合并；合并仅手动、带预览 |
| 快照引用失效 | 历史章节名单/回放错乱 | 旧 node.id 作人物 ID；合并/拆分写别名表；迁移后跑时间轴回归 |
| 写入口遗漏 | 某处改了节点副本导致分叉 | 删除旧 board-scoped 写入口；全局 grep `node.data.states` 写入；纯逻辑断言 |
| 图片失联 | 形象图打不开 | 旧 key 不改名；新 key 用 characterId；GC 改扫人物库；复制为新才复制字节 |
| 当前状态串卷 | 切卷后人物状态莫名变化 | activeStateId 固定在放置节点，不进人物库 |
| 删除节点误删人物 | 其他卷人物消失 | “移除放置”与“删除人物”两个动作、两种确认 |
| 存档体积/兼容 | 旧 v3 导入失败 | persist 继续 merge 迁移；存档升 v4，保留 v3 读取 |
| 切换作品串库 | 两个作品共用人物 | replaceState/载入/新建都整体替换 characters |
| 人物改动不触发“未保存” | 刷新后人物编辑丢失 | `sameStudioContent` 与手动保存 payload 纳入 `characters` |
| 属性改动不刷新快照指纹 | 章节差异/过期检测失真 | `chapterSceneSync` 同时订阅 `characters`，或在生成/切章前重算 |
| 删卷/删节点造成悬空图片 | IndexedDB 泄漏或误删共享图 | 图片 GC 统一以人物库引用为准；删除卷也走 GC（顺带修复现有漏洞） |

## 13. 测试策略

**纯逻辑**

- 迁移：无镜像、完全一致镜像、已分叉镜像、同名不同 ID、旧平铺人物、损坏 states、旧存档 v3；
- 动作：跨卷更新同步、状态切换只改当前放置、删除状态保护、删除人物清理、复制为新 ID/图片隔离；
- 快照：采集/解析/切章回放/别名跟随/缺失降级；
- 查人/时间轴：同一人物多卷合并成一条，同名不同人仍分列；
- 管理器合并：状态冲突、快照影响、同板重复放置。

**部署环境 Playwright（现有用例需同步修改）**

- `e2e_states`、`e2e_character_image`、`e2e_chapter_scene`、`e2e_chapter_board`、`e2e_r3/r4_r5/r6_r7`、`e2e_p3`、`e2e_v3_p2`、`e2e_editor`、`e2e_editor_char_image`、`e2e_canvas`、`e2e_manual_save`、`e2e_migration`；
- 新增：人物库列表/编辑/合并/删除、镜像同步、同名保护、旧档迁移、跨作品切换、只改人物库也出现未保存标记并在保存后恢复、删卷后图片引用正确回收。

**真实模型抽测**

- “修改第一卷张三的基础信息，再问第二卷张三的资料”应读到新内容；
- “把张三复制到第二卷（镜像）后修改任一卷，两卷一致；切换第二卷状态不影响第一卷”；
- 同名不同人时 Agent 不得静默挑选。
