# 剧情推演模拟器设计 · 设计稿（待开发）

> 状态：**设计稿**（2026-10-29 起草，未经实现）。本文回答「是什么、为什么这样设计、落在哪里」，实现前需过一遍 §14 待确认决策。
> 定位：与现有「自上而下」创作流程（目标 → 规则 → 卷 → 大纲 → 正文）并列的第二种模式——**自下而上**：人物在舞台上自主行动，剧情从模拟中涌现，作者观察、挑选、记录成剧情脚本，再交给正文生成。
> 前置阅读：[人物编辑库设计](人物编辑库设计.md)（人物库/放置/快照体系是本模块的地基）、[章节画布与人物状态设计](章节画布与人物状态设计.md)。

## 1. 需求

用户原始诉求：

> 整个小说作品的构建过程基本是自上而下的搭建，我现在需要另外一种模式，可以从下而上地搭建。这是一个剧情推演模拟器：所有在场人物会进入实时模拟状态，可以指定人物记录其行为过程和事件链，作为剧情脚本，用于生成正文。在当前的系统之上，首先对人物有额外的要求，例如有扩展属性，有根据作品需求定义的不同欲望，在不同属性和欲望下产生的行为。同时需要一个系统层面的 skill，用于构建这些属性和行为的定义，使其数值架构合理，运行时能涌现内容。

分解为五条可实现的诉求：

1. **实时模拟**：当前画布上的在场人物（人物库放置）可以进入推演状态，按节拍自主决策与行动。
2. **扩展属性与欲望**：人物在既有状态（basicInfo/identityInfo/relations）之外获得数值化的属性与欲望；欲望随时间增长、被行为满足，驱动行为选择。
3. **行为系统**：作品级定义行为清单（做什么、要求什么条件、满足什么欲望、消耗什么属性），人物「在不同属性和欲望下」产生不同行为。
4. **剧情脚本**：可指定一个或多个人物作为记录对象，其行为过程与事件链沉淀为「剧情脚本」，供正文生成消费。
5. **系统级技能「数值架构师」**：不是用户写作技能，而是系统内置的构建规范——辅助作者定义上述属性/欲望/行为，保证数值架构合理、运行时能涌现剧情。

## 2. 现状：地基与缺口（2026-10-29 调查结论）

### 2.1 可直接复用的地基

| 地基 | 位置 | 对本模块的价值 |
| --- | --- | --- |
| 画布即世界状态 | `types/sim.ts`：环境嵌套容器（parentId + 绝对坐标，`graphGeom.absPositionOf`）+ 人物库放置 | 推演的「舞台」与「人物」不需要新建，直接消费 |
| 人物库 | `WorkCharacter.states`（状态含 basicInfo/identityInfo/relations）+ 放置 `activeStateId` | 推演属性/欲望挂载点；状态语义（「重伤后」）天然支持「不同时期不同欲望结构」 |
| 章节快照管线 | `stores/chapterSnapshots.ts` 纯函数：`collectRegionRoster`（在场/仅提及）、`applyChapterScene` 回放、`stateFingerprint` 指纹、`snapshotStaleness` 差异检测 | 「场景状态采集-冻结-恢复-对比」是现成的时间片原语；推演开始/结束可借用其指纹与回放思路 |
| 生成权威名单 | `engines/chapterContext.ts`：【本章舞台快照】+ 六条硬性规则，`SNAPSHOT_BLOCK_CAP=3600` | 「剧情脚本」注入正文时照此模式做权威约束块 |
| 草稿-确认落地制 | `parseSimOutput` → `SimWriteButtons` / `SimBlockDropRow.drop`，逐块置灰防重复 | 数值架构师产出与脚本写入走同一安全通道，绝不自动生效 |
| 编辑会议轮次编排 | `meetingEngine.ts`：`MeetingTurn.round`、轮循环、`drainRemarks` 用户插话、意见退出 | 多轮编排与流式互斥的先例；但注意它是「编辑部议事」不是角色模拟，不能直接复用其结构 |
| 写作技能槽位模式 | `SimChapter.writingSkillIds`（最多 3 槽）+ `resolveWritingSkills` 按 ID 解析 | 剧情脚本挂章节照抄此模式（`plotScriptIds`） |
| 编辑技能记忆模板 | `memoryTemplates.ts`（`skills/editor-memory/01-08*.md?raw` 内联，固定小节+出厂基线） | **系统级内置规范的现有形态**——数值架构师技能照此实现，不进用户技能库 |

### 2.2 缺口（本模块要补的全部）

1. **模拟时间**：全仓库无 tick/节拍/故事内时钟；`round` 只存在于一次性编辑会议（2-8 轮），`Date.now` 只是真实时间戳。
2. **行为决策循环**：人物只有静态文本设定，没有「感知 → 决策 → 行动」循环。
3. **数值槽位**：人物属性除 `age: number` 外全是文本段；无任何数值系统。
4. **随机与复现**：`Math.random` 仅 3 处且全是 ID 生成；无 seeded RNG。
5. **结构化事件日志**：大纲里「本章事件链 5-9 条」只是文本模板（`DEFAULT_OUTLINE_RULES`），无结构化事件对象，无状态变迁历史。
6. **脚本产物**：输出通道只有设定块/写入块/正文三种，没有推演剧本/事件链格式，没有独立存储。

## 3. 总体架构：数值节拍 + LLM 叙事化的混合引擎

**核心判断（决策 D1）**：纯 LLM 驱动每次行动 = 高频 API 调用（慢、贵、不可复现、难以长时间运行）；纯数值 = 行为干瘪、没有文学性。因此拆成两层：

```
┌─ 定义层（作品级，随存档走）──────────────────────────┐
│ SimPlaySchema：属性定义 / 欲望定义 / 行为定义          │
│ ← 数值架构师技能（系统级）辅助构建 + validateSchema 校验 │
└──────────────────────────────────────────────┘
                    ↓ 实例化
┌─ 推演层（运行时，独立持久化，不进存档）────────────────┐
│ SimPlaySession：seeded 节拍引擎                        │
│ 每 tick 每人物：感知 → 欲望演化 → 效用决策 → 执行 → 事件 │
│ 纯本地计算，零 API 调用，可复现（同 seed 同事件链）       │
└──────────────────────────────────────────────┘
                    ↓ 事件段（批量）
┌─ 叙事层（LLM，低频）───────────────────────────────┐
│ 事件段 + 人物卡 + 环境 + 主导欲望 → 叙事文本           │
│ 导演干预：暂停 / 单步 / 调欲望 / 强制行为              │
└──────────────────────────────────────────────┘
                    ↓ 指定人物的可见事件链
┌─ 记录层（作品级，随存档走）──────────────────────────┐
│ PlotScript 剧情脚本库 ←→ SimChapter.plotScriptIds 槽位 │
└──────────────────────────────────────────────┘
                    ↓ 【剧情脚本】块
┌─ 消费层 ─────────────────────────────────────────┐
│ genChapterContent：舞台块之后注入，事件为既成事实        │
└──────────────────────────────────────────────┘
```

分层收益：

- **试错免费**：调参数重跑 100 tick 不花一分钱、不超时——「推演」的价值就在于反复试。
- **可复现**：同 seed + 同 schema + 同初始值 = 同事件链，作者可以回放、可以分享给他人复现。
- **LLM 用在刀刃上**：叙事化是低频批处理（每 8-12 个事件一次调用），且叙事不反向修改数值——单向数据流，永不脱钩。

## 4. 目标数据模型

### 4.1 定义层：SimPlaySchema（作品级）

随作品存档保存（`studioStore` 新字段，§10）。

```ts
/** 🎬 推演定义（作品级）：属性/欲望/行为的唯一权威定义。
 *  所有 ID 在作品内唯一；运行时只引用不复制定义。 */
export interface SimPlaySchema {
  version: 1;
  /** 扩展属性：人物的数值状态（体力/理智/灵力…），只做可行性门槛与叙事素材，v1 不做效用来源 */
  attributes: SimAttributeDef[];
  /** 欲望：随 tick 增长、被行为缓解的驱动力（效用决策的唯一来源） */
  desires: SimDesireDef[];
  /** 行为：人物可执行的动作，条件-效果对 */
  behaviors: SimBehaviorDef[];
}

export interface SimAttributeDef {
  id: string;            // 'atb-stamina'
  name: string;          // '体力'
  desc: string;
  min: number; max: number;   // 通常 0..100
  defaultValue: number;
}

export interface SimDesireDef {
  id: string;            // 'dsr-revenge'
  name: string;          // '复仇'
  desc: string;          // 何时增长、什么算满足（LLM 叙事化的关键素材）
  min: number; max: number;   // 通常 0..100
  defaultValue: number;
  /** 未被满足时每 tick 增长量（>0）；满足后由行为的 desireEffects 缓解 */
  growthPerTick: number;
  /** 强度达到 threshold 后成为「主导欲望」——叙事锚点（LLM 强调、事件标注） */
  threshold: number;     // 默认 60
}

export interface SimBehaviorDef {
  id: string;            // 'bhv-confront'
  name: string;          // '摊牌'
  desc: string;          // 一句话说明（进事件日志与叙事化 prompt）
  /** 对欲望强度的变化量：负=缓解（满足），正=加剧（如「挑衅」加剧他人愤怒） */
  desireEffects: Record<string, number>;   // desireId → delta
  /** 对属性的变化量：负=消耗，正=恢复（如 睡觉 +体力） */
  attributeEffects?: Record<string, number>; // attrId → delta
  /** 可行性门槛：属性低于 min 则不可选（体力不足不能跑步） */
  requireAttributes?: Record<string, number>; // attrId → min
  /** 场地要求：当前环境类型必须命中其一；缺省=任何环境 */
  requireEnvTypes?: EnvironmentType[];  // 睡觉 → ['bed','room']
  /** 条件：需要独处 / 需要至少一人在同环境（交谈/冲突类） */
  requireSolo?: boolean;
  requireCompanion?: boolean;
  /** 基础权重（同效用时的倾向），默认 1 */
  weight?: number;
  /** 执行后该行为冷却 N tick（防止单行为刷屏） */
  cooldown?: number;
  /** v1 简化移动：执行前先走向的目标环境类型；到达前不可执行 */
  moveTargetEnvType?: EnvironmentType;
}
```

### 4.2 人物侧扩展：状态级覆盖（决策 D4）

欲望结构挂在 **CharacterState**（不是 WorkCharacter 顶层）——「重伤后」的欲望理应不同于「状态0」。但为避免每个状态都要手工配置，采用**覆盖制**：

```ts
// types/sim.ts 的 CharacterState 增加可选字段（additive，旧数据天然兼容）
export interface CharacterState {
  // …既有字段不动…
  /** 🎬 推演档案（可选）：未写出的键回落 SimPlaySchema.defaultValue；
   *  attributes/desires 值为初始强度，结构（有哪些 ID）仍由作品级 schema 决定 */
  sim?: {
    attributes?: Record<string, number>;  // attrId → 初始值
    desires?: Record<string, number>;     // desireId → 初始强度
  };
}
```

作品里没有人配置 `sim` 也能跑（全员 schema 默认值）——冷启动门槛最低；想精细化的人物单独覆盖。

### 4.3 运行时层：SimPlaySession（独立持久化，决策 D2）

```ts
/** 会话运行态：独立 persist 'nc2-simplay-session-v1'，不进作品存档。
 *  记录 workName：载入其他作品/新建作品时检测不符即丢弃（防串库）。 */
export interface SimPlaySession {
  version: 1;
  workName: string;
  boardId: string;                 // 舞台画布（推演期间锁定该画布）
  status: 'idle' | 'running' | 'paused';
  tick: number;                    // 从 0 递增
  seed: number;                    // mulberry32 种子；同 seed 可复现
  actors: SimActorState[];
  events: SimEvent[];              // 环形上限 500，截断最旧（已叙事化的内容进脚本不丢）
  recordedCharacterIds: string[];  // 指定记录的人物（主视角）
  startedAt: number; updatedAt: number;
}

export interface SimActorState {
  characterId: string;
  stateId: string;
  stateFingerprint: string;        // 启动时快照，恢复会话时校验（漂移检测）
  position: { x: number; y: number; parentEnvId?: string };  // 推演坐标（覆盖层，不动画布节点）
  attributes: Record<string, number>;
  desires: Record<string, number>;
  cooldowns: Record<string, number>;  // behaviorId → 剩余 tick
  lastBehaviorId?: string;
}

export interface SimEvent {
  id: string;
  tick: number;
  actorId: string;
  behaviorId: string;
  targetActorId?: string;          // 互动对象（companion 类行为）
  envId?: string;
  envPath: string;                 // 执行时环境路径（冻结，事后画布改动不影响）
  /** 主导欲望快照（决策时强度最高且超阈值者），叙事锚点 */
  dominantDesire?: { id: string; name: string; intensity: number };
  narrated?: string;               // 叙事化后回填
}
```

要点：

- **位置是覆盖层**（决策 D8）：`position` 只画光圈/气泡 overlay，不改画布节点坐标；推演结束画布原样。与 `applyChapterScene` 的「回放会真的搬节点」刻意不同——推演是沙盒，退出无痕。
- **漂移检测**：恢复 session 时校验 `stateFingerprint`；人物状态被改过则提示「人物设定已变化，建议重置推演」。

### 4.4 记录层：PlotScript 剧情脚本库（决策 D3）

作品级库，随存档走；章节通过槽位引用（镜像写作技能模式）。

```ts
/** 📜 剧情脚本：指定人物在一段推演中的行为过程与事件链（作品级库）。 */

  narrative: string;            // LLM 叙事化文本（可整段重生成）
  createdAt: number; updatedAt: number;

export interface ScriptEvent {
  tick: number;
  actorId: string; actorName: string;
  behaviorId: string; behaviorName: string;

```

```ts
// types/sim.ts 的 SimChapter 增加槽位（镜像 writingSkillIds：最多 2 个，解析时忽略已删 ID）
export interface SimChapter {
```

**脚本 ≠ 大纲**（决策 D-extra，见 §14）：v1 保持「本章有大纲才能生成正文」的硬门槛不变；剧情脚本是叠加的**既定事件约束**。v2 再探讨「脚本替代大纲」的自下而上直通模式。

### 4.5 正文注入：【剧情脚本】块

`buildContentSystem` 在舞台块之后、写作技能块之前插入（仅当章节挂了脚本且脚本可解析）：

```
【剧情脚本】（本章既定事件：正文必须呈现，不得矛盾、删除或反转事件结果）
来自推演：「急诊室之夜」｜主视角：李刚｜事件 12 个
- [t12] 李刚 在 仁和医院·急诊室 对 王五 使用 摊牌（主导欲望：复仇）
- [t15] 王五 对 李刚 使用 拂袖而去
- …
叙事：
（叙事文本，cap 1600）
【规则】以上事件为既成事实：可补充过程细节、对白与心理描写，但不得新增改变结果的关键事件；脚本未覆盖的时间段按本章大纲推进。
```

块内自带规则（cap 2400，超限先压叙事段再截断）——**不动 `chapterContext.HARD_RULES` 公共清单**，避免影响无脚本章节的既有行为。

## 5. 数值节拍引擎（决策核心）

新文件 `src/engines/simPlayEngine.ts`，**全部纯函数**（输入状态输出状态，不碰 store、不碰 React），store 外由一个定时循环驱动 `step()`，按批写回 store。

### 5.1 tick 流程

每 tick 对每个 actor 依次执行（顺序按 characterId 排序，保证复现）：

1. **感知**：枚举同环境（同 parentEnvId）其他 actor → 可见人物表；确定当前环境类型与路径。
2. **欲望演化**：`intensity(d) = clamp(intensity(d) + growthPerTick(d), 0, max)`。
3. **冷却递减**：`cooldowns` 各项 -1，归零移除。
4. **移动中判定**：若上一 tick 选择了带 `moveTargetEnvType` 的行为且未到达 → 本 tick 直线向最近的该类型环境中心移动固定步长（v1 无寻路，障碍不处理），到达后下一步可执行。
5. **决策**（§5.2 评分，选最高分行为；全 0 分则「无所事事」保底事件）。
6. **执行**：应用 `desireEffects`（clamp）/`attributeEffects`（clamp）→ 写 `SimEvent` → 设置冷却 → 若带移动意图则记录移动目标。
7. **互动传播**：若行为有正 `desireEffects`（加剧型，如「挑衅」），同时作用于同环境目标 actor 的对应欲望——**这是人物间耦合、涌现冲突的机制**。

### 5.2 效用评分公式

```
score(b) = Σ_d [ intensity(d) × max(0, −desireEffect_b(d)) ]    // 缓解量越大、欲望越强，吸引力越大
         × feasibility(b)                                        // 0/1：属性门槛 × 场地 × solo/companion × 移动可达
         × weight(b)                                             // 基础权重
         × cooldownGate(b)                                       // 冷却中 = 0
         × noise                                                 // seeded rand ∈ [0.9, 1.1]，打破平局
```

- 属性在 v1 **只做可行性门槛与消耗**，不进效用项（避免双系统打架）——「体力耗尽 → 不可行动 → 只能休息」由门槛天然达成。
- 加剧型行为（`desireEffect` 为正的项）不直接产生效用，靠 `weight` 与互动传播制造剧情；评分只看「缓解了什么」。
- **可复现**：`mulberry32(seed)`，每 tick 按 (tick, actorId) 派生子种子；同 seed 同 schema 同初始 = 逐 tick 一致的事件链（测试硬断言）。

### 5.3 涌现从哪里来（数值架构师的职责靶心）

| 涌现机制 | 数值设计要求 |
| --- | --- |
| 欲望冲突 → 摇摆 | 至少一对欲望在行为效果上互斥（满足 A 的行为加剧 B）→ 人物在两者间来回 |
| 条件行为 → 事件 | 有门槛的行为（需要床/需要仇敌在场）不可用时人物被迫做保底行为，条件一旦满足立即爆发 |
| 阈值错拍 | 各欲望 `threshold` 错开 ≥20% → 不同人物、不同时间先后进入主导状态，全场不同时爆发 |
| 互动传播 | 加剧行为把欲望「传染」给他人 → 单人物冲动演化为多人冲突链 |
| 冷却 | 单行为不刷屏；冷却长短本身是节奏设计 |
| 保底行为 | 2-3 个无门槛行为（闲逛/休息）保证任何状态都有动作，日志永不断流 |

### 5.4 运行模式（决策 D9）

- **自动**：定时循环（间隔可调：0.5s/1s/2s/5s），暂停/继续。
- **手动单步**：「下一步」按钮调同一个 `step()`——推演即调试，作者逐拍观察。
- 两模式共用引擎，成本极低，都做。

## 6. LLM 叙事化层

新文件 `src/engines/simNarrator.ts`。**只读数值世界，不回写数值**（单向流）。

- **批量粒度（决策 D6）**：不逐 tick 调用。每次取一段 8-12 个事件（或用户框选范围），打包：事件序列（含主导欲望）+ 涉及人物的卡（basicInfo/identityInfo/relations 截断 + 当前欲望强度）+ 环境路径 → 单次调用产出叙事文本。
- 叙事要求写进系统提示：**逐事件覆盖**（每个事件编号都要在文中呈现顺序与结果）、把主导欲望转译为心理与节奏（不出现「复仇 72/100」这类裸数值）、环境用冻结路径。
- 产出回填 `SimEvent.narrated`（逐段）与 `PlotScript.narrative`（整段）；失败可重试，重试不改变事件。
- **导演干预（v1 范围）**：暂停态下——① 调整某人物某欲望强度；② 强制某人物执行指定行为（下一 tick 锁定）；两者都产生带 `manual` 标记的事件，叙事化时一并覆盖。任意事件注入留 v2。

## 7. 系统级技能：数值架构师

### 7.1 定位

**不进用户写作技能库**（`nc2-writing-skills-v1` 无内置条目是刻意设计）。形态照 `memoryTemplates` 先例：系统内置规范，作为推演面板「AI 构建设计」按钮的系统提示 + 专用产出协议块。它回答的问题：**这个作品该有哪些欲望、哪些行为、数值怎么配，才能跑起来有戏看**。

### 7.2 输入与产出协议

输入（自动收集）：全文目标/全文规则摘要、人物库摘要（姓名/性别/身份/关系，截断）、当前画布环境类型统计、题材提示（用户输入框，可选）。

产出协议块【推演设计】（逐行结构化，解析后过校验器，再以草稿-确认制渲染，用户逐块确认才写入 schema——同 `SimWriteButtons` 模式）：

```
【推演设计】
属性｜体力｜0-100｜默认 80｜体力耗尽只能休息
欲望｜复仇｜0-100｜默认 20｜增长 1.2/拍｜阈值 60｜目睹仇敌或提及旧怨时增长，公开清算后缓解
欲望｜安全｜0-100｜默认 50｜增长 0.6/拍｜阈值 75｜独处黑暗环境时增长，回到安全处所后缓解
行为｜摊牌｜当众向仇敌挑明恩怨｜复仇-35｜安全-15｜需同伴在场｜冷却 8
行为｜蛰伏｜隐忍等待时机｜安全+10｜复仇+5｜冷却 4
行为｜休息｜找个地方恢复体力｜体力+30｜需要 房间/床｜冷却 3
行为｜闲逛｜在环境中走动观察｜无门槛保底｜冷却 2
…
```

### 7.3 设计准则（写进系统提示的硬性要求）

1. 欲望 3-5 个，至少一对互斥/张力对（满足其一加剧另一）。
2. 每个欲望至少 2 个满足行为（不同场地或条件），避免单一解。
3. 至少 1 个阈值属性做可行性门槛。
4. 各欲望 `threshold` 错开 ≥20%。
5. 单行为对单欲望的缓解量 20-40，不允许一拍清空。
6. 必须有 2-3 个无门槛保底行为。
7. 至少 2 个行为依赖他人在场（`requireCompanion`），制造人物间耦合。
8. `growthPerTick` 按目标节奏反推：正常节奏下 20-40 tick 触发一次主导欲望。

### 7.4 本地校验器 validateSchema（纯函数）

LLM 产出先过校验器再渲染确认块：

- **errors**（阻断写入）：引用完整性（desireEffects/requireAttributes 指向的 ID 存在）、数值域（min<max、defaultValue∈[min,max]、effects 落在合法范围）、ID 唯一。
- **warnings**（面板黄条提示，不阻断）：违反 §7.3 各准则（无冲突对/无保底行为/阈值未错开/某欲望无满足行为…）。
- 面板常驻显示 warnings——数值平衡是持续状态，不是一次性检查。

## 12. 风险与应对

1. **叙事与事件脱节/漏事件** → 系统提示强制逐事件编号覆盖；UI 在叙事后按事件数核对并提示缺失。
2. **数值失衡 → 行为单一（全员闲逛）** → validateSchema 准则警告 + 面板行为分布统计实时可见；文档给出调参指南（§5.3 表）。
3. **会话与人物库漂移**（推演中途改了人物状态）→ `stateFingerprint` 校验 + 恢复时提示重置；推演中人物库只读建议（面板提示，不强制锁）。
4. **性能** → 引擎循环在 store 外驱动、按批写回；决策复杂度 O(actors×behaviors) 可忽略；日志上限 500 环形截断；React 渲染按批。
5. **正文上下文膨胀** → 【剧情脚本】cap 2400 + 槽位上限 2 + 已删脚本解析忽略。
6. **复杂度蔓延** → v1 明确不做：寻路（直线移动）、多画布同时推演、关系数值化（relations 保持文本，`requireCompanion` 做粗门槛）、故事内时钟（tick 是抽象节拍，叙事时由 LLM 转译为场景节奏，不写「第 12 分钟」）、任意事件注入、推演结果写回画布。

## 15. 一句话备忘

推演模拟器 = 作品级数值定义（属性/欲望/行为，由系统级「数值架构师」技能辅助构建并经本地校验器把关）+ 本地 seeded 节拍引擎驱动在场人物按效用决策行动涌现事件链 + LLM 低频批量叙事化 + 指定人物的事件链沉淀为剧情脚本库 + 章节槽位引用后以【剧情脚本】既定事件块注入正文生成——沙盒无痕、可复现、与自上而下流程并行互补。
